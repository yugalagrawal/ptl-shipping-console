Client master data, KYC, tiering, rate cards and lane setup — this is where a company becomes a bookable client, and where Sales/Finance sign off on the commercial terms before that happens.

03 Onboarding wizard — the reference to copy

NewClient.jsx is the single most complete example of a multi-step form in the codebase — anyone building a wizard elsewhere (a future multi-step order flow, a fleet onboarding flow) should start by reading this file, not by inventing a new pattern.

StepCapturesNotable pattern
1. Company InfoLegal identity, PAN, address, GST/HSN/SACPincode lookup with a simulated network delay, autofilling city/state
2. Contact InfoPOC, ops/finance email, assigned salespersonTypeahead component for salesperson search
3. Identification InfoOne or more ID documents (GSTIN, Aadhaar, Passport…)Repeatable row group — IdentificationRow, add/update/remove by id
4. Billing InfoContract dates, billing period, credit limit, security deposit, exemptions, CFT→Kg conversion by shipment typeThe densest step — multiple independent repeatable groups on one screen (billing documents, CFT conversions)
5. PricingAuto-suggested tier (from declared volume + payment type), optional override with a required reason, additional chargesSuggestion-with-override UX: system proposes, human can disagree but must say why
6. KYCStatutory documents (PAN, GST certificate, MSME…)Same repeatable-row shape as step 3, reusing docRowSeq so ids never collide across the two lists

The repeatable-row recipe

Every "add another one of these" group in this file (identifications, KYC docs, billing docs, CFT conversions, additional charges) follows the same three-function shape. Copy this, don't reinvent it:

The pattern const [rows, setRows] = useState([{ id: seq++, ...defaults }])
add() → append a row with fresh defaults and the next id
update(id, field, value) → rows.map(r => r.id === id ? {...r, [field]: value} : r)
remove(id) → rows.filter(r => r.id !== id), usually hidden when only one row remains

Suggestion + override

Client tier is computed from declared volume and payment type (suggestTier()), shown as the default, but a human can override it — doing so requires typing a reason (tierOverrideReason), which is the general shape to reuse anywhere a system proposes a number a person might need to overrule with accountability attached.

04 Client lifecycle & where a client "counts"

A client is considered created — and leaves Drafts — the moment Billing Info is confirmed, even though Pricing and KYC aren't done yet. That's intentional: it's already real enough to show up in Sales Admin's queue.

06 If you're building here

  • New wizard field with multiple types/values per client (like CFT→Kg conversion)? Use the repeatable-row recipe above, not a single flat field.
  • New client status? Add it to data/activations.js's status maps, don't hardcode a color in the page.
  • Need a client picker? Import ACTIVE_CLIENTS_SEED — every other module already does.
  • Touching pricing? It's centralized in data/pricing.js on purpose — Create Order and Freight Calculator both call the same computeOrderPricing() so a rate change can't silently drift between the two.
